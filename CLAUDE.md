### Syncthing — large binaries are NOT in git (since 14-Sep-2026)
PDFs, slides, videos, Simulink/Maple/MATLAB binaries are gitignored and replicated
**peer-to-peer by Syncthing**, not by Google Drive. There is no manifest, no
`download.py`, nothing to run after a pull — the files are simply there.

**The rule: git owns the text, Syncthing owns the binaries.**

Four nodes share the folder `dtu`:

| Node | Path | Device ID (first block) |
|---|---|---|
| Desktop (this PC) | `~/DTU` | `YJN3WPF` |
| omarchy (other PC) | `~/DTU` | `SF5B72F` |
| **CT 115 `syncthing`** — always-on, 192.168.50.219 | `/srv/dtu` | `GT6U36Z` |
| CT 114 `learn-sync` | `/srv/learn-sync/repo` | `TMFEEUW` |

The always-on node is what makes this work: the two PCs are almost never awake
together, so they sync *through* the server rather than to each other.

- **What syncs** is decided by `.stignore` at the repo root (committed, so every
  machine gets the same list). It is a **deny-list**: it names the text and source
  that git already carries, and *everything else syncs*. That is the opposite of
  the old manifest, which was an allow-list of "large" extensions and silently
  dropped anything nobody had added to it — that is how the `.slx` Simulink models
  and learn-sync's `.jpg` photos ended up stranded on one machine. A new binary
  format now syncs the day it appears.
- **Web UI** — <http://192.168.50.219:8384> (LAN/Tailscale only, per house rules).
  Credentials on the container in `/root/syncthing-gui-password.txt`.
- **Safety net:** CT 115 keeps **90 days of file versions** (staggered versioning)
  in `/srv/dtu/.stversions`, so a delete that has already replicated is still
  recoverable. The PCs keep no versions.
- **Google Drive is now backup only**, and only CT 115 writes to it:
  `dtu-drive-backup.timer` mirrors `/srv/dtu` → `gdrive:DTU/Backup-Syncthing`
  nightly at 04:15, moving anything deleted into a dated
  `Backup-Syncthing-trash/` folder instead of dropping it. **No PC has an rclone
  token any more** — which is the whole point: the token expiring
  (`invalid_grant`) is what broke the old pull on 14-Sep-2026.
- The old `gdrive:DTU/DTU_Vault_Assets` folder from the manifest era is left
  untouched as a historical copy. Delete it once you trust the new backup.

  stay excluded: each machine keeps its own git state, and syncing `.git` between
  machines on different commits corrupts the repo.
- ⚠️ **`.stignore` itself is in the ignore list** and travels by git instead. Edit
  it in the repo, commit, and pull it on the other machines — editing it in the

  it needs the file copied to `/srv/dtu/.stignore` by hand after a change.
- ⚠️ A few extension-less vendored text files (`LICENSE`, `Makefile`, cJSON test
  inputs) are named explicitly in `.stignore`. Anything similar that appears later
  will sync harmlessly unless added — it is a deny-list, so the failure mode is
  "syncs something it needn't", never "silently loses a file".

### 🚩 THREE EXAM GOTCHAS (always worth memorising — these come up)

1. **AND/OR opcode swap.** Team's hardware: `OR = 0001000, AND = 0001001`. Textbook (Mano/Kime pp.490, 493) + Java assembler + lecture-10 slide 9: opposite. **The PWF spec footnote on page 1 acknowledges the textbook discrepancy.** Use `dsdasm` (team's Python assembler), NOT the Java tool — Java emits wrong opcodes for AND/OR.

2. **3-bit LDI immediate limit.** `LDI` can only load 0..7 (3-bit field zero-extended). For higher values (e.g. 0xFA = MR2/LEDs), use:
   ```asm
   NOT R2 R4         ; R2 = NOT 0 = 0xFF (R4 is 0 after reset)
   LDI R4 5          ; R4 = 5
   SUB R3 R2 R4      ; R3 = 0xFF - 5 = 0xFA → addresses LEDs
   ```

3. **BRZ/BRN test R[SA], NOT the previous instruction's flag.** Z/N are *combinational* outputs of the FU. In BRZ's EX0, the IDC defaults route `R[SA]` through the ALU (pass-A, FS=0000), and the resulting Z is what the IDC samples. So `BRZ A1, off` literally means "if R1 == 0, branch" — NOT "if the previous result was 0". To branch on an earlier op's result, put the destination in BRZ's SA slot: `add D2 A1 B3 ; brz A2, target`.

### 🚩 The hardware bug discovered 27-May-2026

`team/PWF/sources/hdl/PortReg8x8.vhd:71` writes MR1 from `Data_In(15 downto 8)`, but `Zero_Filler_2` always pads those bits to 0. **So any `ST` to address 0xF9 always writes 0 — the left two 7-seg digits cannot show non-zero data on the as-submitted hardware.** The team's `addsub_calc.asm` comment notes this cryptically (*"MR1 er reelt altid 0 pga. Zero_Filler_2"*) but never fixed it. One-line fix: change `Data_In(15 downto 8)` to `Data_In(7 downto 0)` matching MR0/MR2. Documented in detail in chat history (was found while testing a `show_a_b.asm` program). Good exam talking-point: "tell me about a design decision that turned out to be wrong".

### 🚩 The b899da1 IDC fix (Jonas, 13-May-2026, in team repo)

A real correctness fix late in the project. Two bugs:
- **EX2 had `BX` defaulted to the imm-field** instead of pointing at R8 — the Shifter was shifting the wrong register, SRM produced garbage. Fix: explicit `BX <= "1000"` in EX2.
